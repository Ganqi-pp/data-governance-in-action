# 数据质量规则与整改验收

> 质量治理最容易做成两件事：一是“感觉有问题”，二是“报表变绿了”。本文用一套可执行的规则、可解释的评分和可复检的验收，避免这两件事。

## 1. 六个质量维度

| 维度 | 回答的问题 | 本项目典型规则 |
| --- | --- | --- |
| 完整性 | 该有的有没有？ | 信用代码、名称、日期、电话、地址非空 |
| 准确性 | 值对不对？ | 信用代码校验位、金额区间、日期合法 |
| 一致性 | 跨字段/跨表是否矛盾？ | 地址与区划一致、等级与评分一致、办结≥提交、信用记录能关联主体 |
| 唯一性 | 有没有重复？ | 信用代码唯一、工单号唯一、评价号唯一 |
| 有效性 | 格式/码值是否规范？ | 手机号、邮箱、行业码、状态码、类型码 |
| 及时性 | 是不是太旧？ | 更新时间不超过 365 天 |

## 2. 评分公式

### 2.1 规则级

```text
违规率 = 违规记录数 ÷ 校验记录数
规则达标 = 违规率 ≤ 容差
```

容差是治理 SLA，不是“允许错”。高严重度规则容差 0—0.5%，低严重度 1%—2%；超容差进入整改工单，容差内记为观察项。

### 2.2 记录级健康度

```text
表健康度 = 100 × (1 − 存在任一质量问题的主键数 ÷ 记录总数)
综合健康度 = Σ(表权重 × 表健康度)
```

表权重：市场主体 0.5、信用评价 0.3、诉求工单 0.2。

示例：市场主体 1,240 条，有 545 条至少存在一个问题：

```text
100 × (1 − 545 ÷ 1240) = 56.05
```

**为什么不用“问题条数 ÷ 总行数”？** 一条记录可能同时缺电话、状态错误、区划不一致，简单相加会重复扣分，分数被少数“问题大户”拉低，无法反映“多少条记录可用”。

**为什么不用“规则通过率”做唯一分数？** 44 条规则里可能有 20 条是低风险格式检查，全部通过也不代表数据可用。规则达标率作为辅助指标单独披露。

### 2.3 数据可用率

```text
数据可用率 = 治理后记录数 ÷ 原始记录数
```

隔离数据不参与质量分，但必须在可用率中披露。否则“删掉问题数据”就能把分数刷到 100。

| `credit_rating` | 11 | 信用代码非空/可关联、评分 0—100、等级枚举、等级与评分一致、评级日期非空/非未来、机构非空、更新新鲜度、评价号唯一 |

### 3.1 规则模板

| 类型 | 参数 | 用途 |
| --- | --- | --- |
| `not_null` | field | 非空检查 |
| `unique` | key | 业务主键唯一 |
| `regex` | pattern | 手机号、邮箱等格式 |
| `enum` | values | 码值枚举 |
| `range` | min/max | 金额、评分、满意度 |
| `date_valid` | field | 日期可解析 |
| `date_not_future` | field | 不晚于数据截止日 |
| `date_order` | start/end | 时间先后关系 |
| `conditional_not_null` | condition/values | 特定状态下必填 |
| `referential` | ref_table/ref_field/filter | 码表/主体关联 |
| `freshness` | days | 更新时效 |
| `uscc` | - | GB 32100 校验位 |
| `custom_sql` | sql | 复杂跨字段规则 |

新增规则只需在 JSON 中加一段配置，不需要改引擎；这是“治理平台配置化”的最小实现。

## 5. 问题定位

每条问题包含：

```text
规则编号 + 规则名 + 表 + 字段 + 记录主键 + 证据 + 严重度 + Owner + SLA + 整改建议
```

例如：

```text
DQ-REG-010 | 联系电话符合手机号格式 | market_register | contact_phone
REG2026000123 | 联系电话不符合格式规范 | 高 | 企业服务科 | 3 天
建议：去除分隔符、+86 前缀，全角转半角后重新校验；仍不合规的置空。
```

这就是“问题定位”与“泛泛而谈”的区别：能定位到具体记录，才能派单、才能复检。

## 6. 清洗与整改

### 6.1 可自动修复

| 问题 | 处理 |
| --- | --- |
| 手机号带 `-`、空格、`+86`、全角数字 | 归一为 11 位 |
| 企业名称首尾空白、全角空格 | 去空白、压缩空格 |
| 经营状态“正常/在营/开业” | 映射为标准码值 |
| 行业名称代替代码 | 按码表映射 |
| 地址与区划代码不一致 | 按住所中的县名修正区划 |
| 信用等级与评分不一致 | 按评分区间重算等级 |
| 重复信用代码 | 保留更新时间最新的一条 |
| 办结时间早于提交时间 | 置空并回退状态为“办理中” |

### 6.2 无法自动修复 → 隔离

| 问题 | 原因 |
| --- | --- |
| 信用代码校验位错误/缺失 | 不能猜，必须回源 |
| 关键日期缺失/非法/未来 | 时间序列不能造 |
| 信用/诉求记录关联不到主体 | 主体不存在或代码错误 |
| 重复记录中较早的一条 | 保留最新，旧记录留证据 |

隔离区不是“垃圾桶”：它有原因码、原始行、创建时间，等待人工核实；隔离量在可用率中披露。

本项目共执行 369 次修复动作，TOP 5：

| 动作 | 次数 |
| --- | ---: |
| 手机号格式归一 | 51 |

## 7. 整改验收

### 7.1 验收方法

不是比较总分，而是：

1. 保存治理前每条问题的 `(规则编号, 表, 主键)`；
2. 治理后对 DWD 层重跑同一套规则；
3. 逐条判断：
   - 同一主键不再命中同一规则 → **已修复**；
   - 主键进入隔离区 → **已隔离**；
   - 仍命中且规则未达标 → **待整改**；
   - 仍命中但规则整体达标（容差内）→ **观察项**；
   - 治理后新出现 → **新发现**。

### 7.2 验收结果

| 状态 | 数量 | 含义 |
| --- | ---: | --- |
| 已修复 | 428 | 同规则复检通过，自动验收 |
| 已隔离 | 198 | 无法自动修复，进隔离区 |
| 待整改 | 106 | 仍违规，已派单 |
| 观察项 | 128 | 容差内，持续监控 |
| 治理后新发现 | 4 | 清洗暴露的新问题 |

- 自动修复率：**49.8%**
- 处置率（修复 + 隔离 + 观察）：**87.7%**
- 待整改集中在：联系电话缺失 65 条、地址缺失 12 条、内容缺失 12 条、办结时间缺失 13 条、更新时间缺失 8 条。

### 7.3 验收标准

| 项目 | 标准 |
| --- | --- |
| 高严重度问题 | 修复率 ≥ 95%，未修复必须有书面说明 |
| 中低严重度问题 | 处置率 ≥ 85% |
| 隔离数据 | 100% 有原因码与责任人，30 天内核实 |
| 复检 | 同一规则、同一主键、同一数据截止日 |
| 证据 | 问题台账、修复日志、复检结果三者一致 |

## 8. 规则有效性验证

很多项目只说“发现了 N 个问题”，却无法证明规则有效。本项目在造数阶段注入 33 类、833 条缺陷，并保存清单 `data/raw/_defect_manifest.json`；规则跑完后逐类比对：

```text
检出率 = 命中注入缺陷的记录数 ÷ 注入缺陷记录数
```

结果：

| 指标 | 结果 |
| --- | ---: |
| 缺陷类型覆盖 | 32 / 33（97.0%） |
| 缺陷记录检出 | 812 / 833（97.5%） |
| 未覆盖类型 | 企业名称截断（语义错误，格式规则无法识别） |

例如 `PHONE_FORMAT` 注入 70 条，`DQ-REG-010` 检出 70 条，检出率 100%；`DATE_INVALID` 注入 8 条，检出 6 条（2 条是 `2024.05.12` 这类可解析格式，SQLite 日期函数不认，清洗层能解析），检出率 75%。这种“不完美”比“全部 100%”更可信。

完整结果见 [`reports/rule_effectiveness.csv`](../reports/rule_effectiveness.csv)。

## 9. 反模式清单

| 反模式 | 为什么错 | 本项目怎么做 |
| --- | --- | --- |
| 删掉问题数据刷分 | 分母变小，分数虚高 | 隔离 + 披露可用率 |
| 只报问题数，不报影响 | 1 条和 1 万条看起来一样 | 记录级健康度 + 影响行数 |
| 规则写死“全部通过” | 无法发现新问题 | 44 条规则 + 容差 + 未覆盖披露 |
| 只做字段级检查 | 正文里的身份证号发现不了 | 内容级扫描 |
| 整改只看报表 | 同一问题可能被“平均”掉 | 同主键复检 |
| 指标口径各算各的 | 看板与月报对不上 | 指标 SQL 统一配置 |

## 10. 进一步改进

1. 增加跨表一致性规则（如信用评分与投诉满意度相关性异常）；
2. 引入历史趋势，识别“质量分突然下降”；
3. 对语义质量引入外部核验或大模型辅助抽检；
4. 规则试运行机制：新规则先影子运行 2 周，再纳入考核；
5. 把整改 SLA 接入工单系统，自动升级。
