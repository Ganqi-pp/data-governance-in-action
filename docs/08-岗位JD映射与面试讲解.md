## 2. 三分钟讲法

> 面试官说“介绍一下你的数据治理项目”，用这个结构，控制在 3 分钟。

**背景（20 秒）**
“我做过一个市场主体服务的数据治理项目，数据来自登记系统、信用平台和 12345 热线，共 3 张表、3,690 条。问题是标准不统一、联系方式缺失、诉求正文含个人信息，出了问题找不到责任人。”

**做法（60 秒）**
“我先建标准和目录，把 29 个字段的定义、类型、码表、Owner 定下来；然后用 44 条 SQL 规则做质量基线，覆盖六个维度。能自动修的，比如手机号格式、状态码、区划、信用等级，在清洗层修；不能修的，比如信用代码校验失败、关键日期非法，进隔离区，不删数据。治理后用同一套规则、同一批主键复检，把问题标成已修复、已隔离、待整改、观察项，形成带 Owner 和 SLA 的台账。最后做字段级和内容级分类分级、脱敏共享、资产登记和字段级血缘。”

**结果（40 秒）**
“综合健康度从 72.2 到 90.9，规则达标率从 40.9% 到 88.6%。860 条问题里 428 条自动修复、198 条隔离、106 条待整改。为了证明规则有效，我在造数时注入了 33 类缺陷，检出率 97.5%，并且明确有一类语义缺陷规则覆盖不了。脱敏共享文件做了残留扫描，0 处残留。”

**反思（40 秒）**
“这个项目最大的价值不是分数，而是把‘问题—责任—验收’跑通了。剩下的 106 条主要靠源系统补录，治理层不能改数；企业名称截断这类语义问题需要人工抽检或外部核验。下一步我想接 DataHub/Atlas 和调度平台，把血缘和规则做成可持续运营的。”

**收尾（20 秒）**
“项目零依赖，一条命令可以复现，所有数字来自脚本，代码、报告、模板都在 GitHub 上。”

## 3. 十分钟讲法（按治理链路）

1. **体系（1 分钟）**：组织、RACI、制度、KPI、路线图；强调业务 Owner 负责，Steward 执行。
2. **标准与目录（2 分钟）**：29 字段、码表、标准编号、自动采集与剖析；举“手机号 11 位、去 +86”的例子。
3. **质量（3 分钟）**：六维、44 条规则、记录级评分、问题定位；举“地址与区划不一致”的跨字段规则。
4. **清洗与隔离（1.5 分钟）**：可修复 vs 不可修复；隔离原因；可用率 94.4%。
5. **整改验收（1.5 分钟）**：同规则同主键复检；428/198/106/128；反模式“删数据刷分”。
6. **安全与资产（1 分钟）**：分级、内容扫描、脱敏、残留 0；15 项资产、Owner、共享属性。
7. **血缘与指标（1 分钟）**：31 条字段映射、impact 命令、5 个指标口径统一。
8. **反思与规划（1 分钟）**：语义质量、平台化、权限网关。

## 5. 常见追问与回答

### Q1：为什么健康度是 90.9，而不是 95 以上？

因为剩余问题主要依赖源系统补录：联系电话缺失 65 条、地址缺失 12 条、内容缺失 12 条、办结时间缺失 13 条、更新时间缺失 8 条。治理层可以清洗格式、统一码值、隔离脏数据，但不能伪造缺失值。把目标定在首年 90、三年 95，是为了先跑通机制，再逐步抬高，不是为不达标找理由。

### Q2：为什么用记录级评分，而不是规则通过率？

规则通过率会被“低风险规则多”稀释，也不能反映多少条记录可用。记录级评分回答的是“1,240 条里有多少条至少有一个问题”，更接近业务感受。规则达标率作为辅助指标单独披露，两者一起看。

### Q3：隔离数据是不是在“藏问题”？

不是。隔离数据有原因码、原始行、责任人，且在可用率中披露（207 条，5.6%）。删除才会藏问题，隔离是把问题留在台账里。报告里也明确写了“待整改 106 条”，没有假装全部修完。

### Q4：怎么证明规则有效，而不是规则和造数串通？

造数脚本先按业务规则生成“干净数据”，再按类型注入缺陷并保存清单；质量规则独立从 JSON 配置加载，不读取清单。报告用清单逐类比对检出率，并公开未覆盖类型。规则和造数是两条独立链路，只是共享同一套业务定义。

### Q5：分类分级为什么既做字段又做内容？

字段名可能骗人：`content` 里可能有身份证号，`remark` 里可能有电话。字段级覆盖“已知”，内容级覆盖“未知”。本项目在 1,500 条工单里命中 150 行个人信息，脱敏后再扫残留为 0。

### Q6：字段级血缘怎么保证不漂移？

血缘映射来自转换配置 `transformations.json`，不是手写文档；CI 校验 DWD 字段是否都有映射。表级拓扑来自 `lineage.json`，变更前跑 `impact`。这样文档和实现至少有一个强约束，不会完全各写各的。

### Q7：如果数据量到 TB 级，这套东西还能用吗？

SQLite 是沙箱，生产要换数仓/Spark；但规则 SQL、评分公式、分类分级、资产模型可以平移。元数据接 DataHub/Atlas，调度接 Airflow/DolphinScheduler，规则引擎可以换 Great Expectations 或自研。项目重点是把治理逻辑跑通，不是证明 SQLite 能扛 TB。

### Q8：你最大的不足是什么？

三点：一是语义质量没解决，名称截断、地址错别字规则识别不了；二是没接真实平台，血缘和元数据还是配置驱动；三是安全控制是示例，没有权限网关和动态脱敏。这三点都在 Roadmap 里，优先级分别是语义抽检、平台接入、权限网关。

### Q9：如果让你重做一次，会怎么改？

我会先做“指标—标准—质量”的闭环，而不是先写清洗代码；因为指标会倒逼标准，标准会倒逼质量规则。然后更早引入历史快照，否则只能看单期分数，看不到趋势。最后会把隔离数据的处理流程做成工单，而不是只写原因码。

### Q10：这个项目里你最有成就感的是什么？

不是 90.9 分，而是“同主键复检”那一套：它把“治理”从一份报告变成了可验证的流程。每一条问题都能回答“修没修、谁负责、什么时候到期、复检结果是什么”。

## 8. 不要过度承诺

- 不要说“我搭建了企业级数据治理平台”——它是一个可运行的教学/作品项目；
- 不要说“质量提升 18 分，业务收益多少”——没有真实业务收益数据；
- 不要说“完全自动化”——仍有 106 条待整改、198 条隔离需要人工；
- 不要把模拟数据说成真实政务数据——所有数据均为虚构，已在 README 和数据说明中标注。

诚实说明边界，反而更容易得到面试官信任。
